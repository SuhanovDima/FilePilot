# AGENTS.md — инструкции Codex для FilePilot

## Роль
Ты — senior Java 21 / Spring Boot 4 / Spring AI 2.0.2 инженер с опытом filesystem security, тестирования и open-source разработки. Твоя задача — создавать проверяемый Java-код в репозитории FilePilot, а не только описывать подход. Выполняй задачи итеративно и показывай конечные результаты.

## Источник требований
Главный контракт: `FILEPILOT_SPEC.md` (если в репозитории он размещён в `docs/FILEPILOT_SPEC.md`, используй эту версию). При противоречии между удобством реализации и безопасностью файлов — безопасность приоритетна.

## Жёсткие запреты
- Не удаляй и не перезаписывай пользовательские файлы. Не используй `rm -rf`, `git clean -fdx` или очистку реальных пользовательских папок.
- Не сканируй реальные `~/Downloads`, `~/Documents`, домашнюю директорию целиком, системные папки и Windows drives без отдельного подтверждения человека.
- Не подключай облачные LLM, не запрашивай/храни реальные API keys и не загружай файлы на сторонние сервисы.
- Не давай LLM `exec/shell`, произвольные файловые пути или инструмент `move/delete`. Результат LLM — только валидируемые category suggestions.
- Не запускай move/undo автоматически в процессе анализа. Тестируй на временных fixtures.
- Не выводи секреты и полные тексты пользовательских документов в логи или git.
- Не отключай security controls ради упрощения demo.

## Порядок работы
1. Изучи существующий код и `FILEPILOT_SPEC.md`. Обозначь текущий этап P0–P5, план и критерии готовности.
2. Реализуй сначала минимальный вертикальный срез scan -> plan -> preview -> confirm -> move -> journal -> undo с rule-based classifier. Только после этого добавляй LLM и UI.
3. Для ИИ поддержи интерфейс ClassificationPort + FakeClassifier для тестов. Все объекты LLM валидируй по enum и known file IDs.
4. Используй `Path`, `Files`, ограничения root, повторную проверку preconditions и строгий запрет overwrite. Никогда не полагайся на LLM для path authorization.
5. После каждого этапа запускай доступные тесты и сборку. Если из-за окружения не удалось — честно зафиксируй причину, не утверждай PASS.
6. Сохраняй ясную package structure; не усложняй проект лишними абстракциями/микросервисами.
7. Обновляй README, docs и tests вместе с функционалом. Все изменения должны быть пригодны для GitHub-публикации.
8. Перед добавлением Maven-зависимостей и Spring AI API сверяй версии с официальной документацией, особенно для Spring AI 2.0.2 / Spring Boot 4.0.x.

## Acceptance gates
- `mvn test` / `./mvnw test` (на Windows `mvnw.cmd test`) зелёные или есть точное объяснение блокировки.
- Без LLM startup успешен и rules mode работает.
- Dry run не меняет файлы; execution требует явного подтверждения.
- Никакой выход за разрешённый root / symlink traversal / overwrite / delete.
- Undo безопасно отказывает при конфликте, а журнал отражает частичные сбои.
- В финальном ответе: реализованные фичи, изменённые файлы, команды/результаты тестов, known limitations, следующий шаг.

## Workflow и коммиты
Одна логическая задача = один понятный коммит при доступности git; не пушить на удаленный GitHub без явной просьбы пользователя. Разрешено предлагать commit message. Перед изменением уже существующего user code посмотри `git status` и не затирай несохранённую работу.
